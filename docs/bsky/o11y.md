# AppView observability (OpenTelemetry)

The bsky AppView emits OTLP traces via the OpenTelemetry NodeSDK, replacing
the previous Datadog-specific `dd-trace` tracer. This mirrors the PDS
migration; where the two diverge is noted below.

## Files

### `packages/bsky/src/telemetry.ts`

Side-effect entrypoint that starts the NodeSDK. Loaded before any other
module via `node --import @atproto/bsky/telemetry` (exposed through the
`"./telemetry"` export in package.json); the bsky Dockerfile CMD does this.
It is never imported by library code.

Configuration comes from conventional `OTEL_*` environment variables, or a
YAML file via `OTEL_CONFIG_FILE`. The script registers a curated set of
instrumentations rather than `auto-instrumentations-node`: http, express and
undici (with request hooks that normalize XRPC paths into a low-cardinality
`http.route` of the form `/xrpc/<nsid>`), pino, and node runtime metrics.

Counterpart: `packages/pds/src/telemetry.ts`, from which it was ported
nearly verbatim. Differences: the PDS additionally instruments aws-sdk,
better-sqlite3 and ioredis (bsky's AppView runtime uses none of them —
bsky's redis wrapper only serves an unused cache and tests), and bsky has
no `metrics.ts` yet (the PDS ships a first counter there).

### `packages/bsky/src/rpc-tracing.ts`

A connect-rpc client `Interceptor` that creates CLIENT spans for RPC calls,
following the OpenTelemetry RPC semantic conventions. It exists because
`@opentelemetry/instrumentation-http` does not cover `node:http2`, which
connect's transports use — without it, dataplane calls (the AppView's
hottest dependency) would produce no spans at all.

It depends only on `@opentelemetry/api`, so it is a cheap no-op when no SDK
is registered — safe for tests, dev-env, and library consumers. It also
injects `traceparent` into outgoing requests, so instrumented servers join
the same distributed trace.

No PDS counterpart: the PDS's outbound calls are XRPC-over-undici, which
`UndiciInstrumentation` already covers. Both packages carry a `@TODO` to
replace the XRPC request hooks with dedicated Xrpc instrumentations; this
interceptor is the analogous stopgap for connect-rpc.

Wired into the client factories (not call sites) in:

- `packages/bsky/src/data-plane/client/index.ts` — `peer.service: 'atlantis'`
- `packages/bsky/src/bsync.ts` — `peer.service: 'vortex'`, `peer.interface: 'bsync'`
- `packages/bsky/src/courier.ts` — `peer.service: 'courier'`
- `packages/bsky/src/rolodex.ts` — `peer.service: 'rolodex'`

### `services/bsky/Dockerfile`

Loads the entrypoint (`--import=@atproto/bsky/telemetry` in the CMD) and
carries the label `social.bsky.appview.telemetry="otel"` so deployment
tooling can distinguish otel images from dd-trace ones (the PDS image uses
`social.bsky.pds.telemetry`). The old `services/bsky/tracer.ts` (dd-trace)
is gone, as is `services/pds/tracer.ts` on the PDS side.

## Gotchas

- **Telemetry is opt-in, inverting the spec.** The SDK stays off unless
  `OTEL_SDK_DISABLED=false` is set explicitly — the opposite of the standard
  semantics for that variable, matching the PDS telemetry script. If you run
  a smoke test and see no spans, this is why.

- **`peer.service` must match the remote's self-reported `service.name`.**
  Atlantis reports itself as `atlantis` and vortex as `vortex`; a mismatched
  client-side assertion makes service maps render two nodes for one service.
  The dd-trace-era name `dataplane-bsky` is gone for this reason, and the
  bsync client says `vortex` with a bsky-specific `peer.interface: 'bsync'`
  attribute recording the interface name we know it by. Courier wires up
  otelconnect interceptors but never registers a tracer provider, so it
  currently reports nothing — if that changes, its chosen `service.name`
  needs to match our `courier`.

- **We emit current RPC semconv; the ecosystem mostly doesn't yet.**
  `rpc.system.name`, fully-qualified `rpc.method`, `rpc.response.status_code`
  and `error.type` — the attributes they replace (`rpc.system`,
  `rpc.service`, `rpc.grpc.status_code`, `rpc.connect_rpc.error_code`) are
  deprecated but still what otelconnect (and thus atlantis) emits.
  Attribute-based queries joining client and server spans will see both
  vocabularies until the ecosystem catches up; span names and trace IDs are
  unaffected. `rpc.response.status_code` is Release Candidate stability, not
  yet frozen.

- **Datadog dashboards keyed on old names need updating.** The dd-trace
  `service.name=dataplane-bsky` / `resource.name` conventions no longer
  exist; the equivalents are `peer.service=atlantis` and the span name.

- **Traces join up with atlantis for real.** Its otelconnect interceptor is
  constructed with `WithTrustRemote()`, so it extracts our `traceparent` and
  parents its server spans under our client spans — one trace ID from the
  express request through the dataplane.
