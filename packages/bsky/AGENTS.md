# AppView hydration

- Endpoint-specific viewer block checks must honor `HydrateCtx.skipViewerBlocks` for the trusted moderation service, while preserving viewer block metadata and mute filtering.
- In `hydration/external.ts`, keep shared types above `ExternalHydrator`; place helpers and their specific types below the class.
- `ExternalHydrator` generic record lookups decode record bodies without collection-specific validation. Validate against the relevant Lexicon before using typed fields; do not apply parse-mode defaults to stored records.
- `getRecordsByURI`/`getRecordsByRef` split input into sequential requests of at most `MAX_RECORDS_PER_REQUEST` (the dataplane rejects more than 100 URIs), pairing results positionally per request. Any failed request rejects the whole call; never return partially fetched batches. Bound requests there, not in callers or traversal.
- `Views.externalRecordView` consumes `HydrationState.externalRecords` (latest versions), `externalRecordBacklinks` (target URI → available source URI samples), and `externalRecordBacklinkCounts`. Hydrate referenced publications, gallery item/photo records, backlink source records, labels, and profiles before building views. Counts are independent of the sampled previews.
- External view builders keep strict Lexicon validation (`$matches`). Handle third-party records that violate their own published lexicon with a minimal compatibility override (see `lexicons-overrides/README.md`), not by loosening view validation.
- Streamplace uses a declared HTTP(S) URL or falls back to its AT URI. A stream is active only without `endedAt` and with a `lastSeenAt` within `LIVESTREAM_HEARTBEAT_WINDOW_MS` (2 minutes) of `now`, on either side; record `idleTimeoutSeconds` and `createdAt` are ignored.
- Atmosphere Explore uses each worker item’s `canonicalUri` as its sole hydration/view root; a missing or invalid root skips the item with no fallback or backfill. With the `AtmosphereExploreArticlesIrisEnable` gate off, worker groups also supply articles; with it on, up to 10 Iris `site.standard.document` roots (fetched concurrently with the worker) are the exclusive article source when the call succeeds with a nonempty articles list: worker articles are ignored and worker location/topic selection does not apply to them. Every list is capped at 10: selected record-backed lists (including Iris articles) are shuffled before hydration with scheduled featured items first, and presentation preserves that order; apps are capped at 10 in worker order. Worker ingestion is best-effort per item: malformed banners, groups, and app cards are skipped without failing siblings or the request; only the first 100 entries per worker section are examined. Call Iris directly with request-scoped headers and abort signals, explicitly enabling XRPC response validation even outside debug mode; do not add a separate response parser. Keep article-root validation and the 10-item cap. A successful empty Iris list falls back to worker-curated articles and retains Iris's rec ID; a nonempty Iris list fully removed by root filtering or hydration does not trigger curated fallback. Catch Iris request and response-validation failures (rethrowing request aborts): log a warning and fall back to worker-curated articles with no rec ID; worker failures stay fatal, and the gate-on missing-Iris-client 501 is unchanged. The worker fetch retains its decoded-byte limit and deadline. Each list is an `{ items, recIdStr? }` section; `articles.recIdStr` comes from a successful Iris response, including the empty-list worker fallback, rather than identifying the source of the returned articles. Keep root validation in `getAtmosphereExploreTab.ts`; one shared hydration traversal discovers publications and other dependencies.
- Exact-ref hydration maps are keyed by the branded `ExactRecordKey` from `genericRecordKey({ uri, cid })`, not URI alone; `parseGenericRecordKey` accepts only those keys and throws on malformed ones. Unavailable records are `null`, and takedowns are excluded unless explicitly requested.
- Preserve `truncated` from actor backlink lookups: an empty target entry in a truncated batch does not prove the actor has no links.
- Generic external-view wrappers populate only the generic indexes and follow a document's publication through normal dependency discovery (a second lookup after the document, with its own labels and profiles). Saved-post hydration (`hydratePosts`) hydrates every pinned `associatedRefs` root of any collection through one generic exact-ref traversal and returns only generic state; `Views.externalEmbedFromStandardSite` selects pinned Standard.site roots with `getSiteStandardRecordsFromRefs`, reading only each ref's exact key (latest dependencies never satisfy a pin). Never replace a pinned publication with its latest version.
- Pass all external URIs to `Hydrator.hydrateExternalViewDependencies`; dispatch by URI collection and validate records inside it. Batch new dependencies through `hydrateEmbedExternalViewFromUris`, sharing a `seenRecordKeys` set (including null lookups) across nested passes. Follow only complete DID-based record URIs.
- `hydrateEmbedExternalViewFromUris` nulls each generic record (in `externalRecords` and `externalRecordsByRef`, keeping keys) that has an actionable takedown label (unless `includeTakedowns`) or an explicitly `null` owner actor, before dependency expansion. Hiding is per record: never propagate it to targets or dependencies, and leave backlink counts and samples unadjusted.
- Dependency dispatch in `hydrateExternalViewDependencies` may register several backlink queries per target (each with its own collection and limit; results are unioned) and discovers direct references (e.g. `document.site`, `gallery.item.item`) through `discoveredUris`; direct-only passes issue no backlink or count calls. Validate authored references with `recordUriOf`; do not validate dataplane backlink URIs.
- External hydration traversals share a `seenRecordKeys` set that both wrappers filter against at entry by `genericRecordKey(ref)` (bare URI for latest, `uri@cid` for exact), so each lookup runs once per traversal (null results stay seen). `ExternalHydrator.MAX_EXTERNAL_HYDRATION_PASSES` hard-caps chained batches (root is pass 1; `hydrationPass` is threaded through both methods and never reset). Physical request chunks within a batch consume no passes. At the cap, keep partial state, leave skipped URIs unseen, and warn.
- External-view counts, backlink pages, and nested dependency batches are best-effort: log failures and leave their state absent (a successful empty page is `[]`), and builders consume partial state, so galleries may be empty. Root fetch errors still propagate. Each recovered failure sets the tracker's `partial` flag, so the traversal reports `partial` unless it was `capped`, which takes precedence. Don't add failure-policy machinery.
- Thread the optional `hydrationMetrics` tracker through every nested external hydration call (wrappers and `hydrateExternalViewDependencies`). Only the call without one owns the traversal and reports `events.externalHydrationTraversal` once; omitting it in a nested call double-reports. Count lookups at batch scheduling, never from map or seen-set sizes, and keep totals out of metric attributes. `batches` counts logical passes, not RPCs. The reported endpoint is `HydrateCtx.xrpcEndpoint`, a closed union of NSIDs that handlers set from their method's `$lxm`. Discovery counts each inspected ref as resolved if available after moderation; the first discovery call's refs are roots (tracked by a flag, not pass number), later ones dependencies.
- `hydrateEmbedExternalViewFromUris` and `hydrateEmbedExternalViewFromRefs` are thin wrappers over one pipeline and one collection dispatch. Latest lookups are identified by URI (`externalRecords`); exact versions by `genericRecordKey({ uri, cid })` (`externalRecordsByRef`). Both identities share `seenRecordKeys`, and one never implies the other; a latest fetch does not mark its returned version as an exact lookup. Dependency discovery takes `ItemRef[]` and inspects every pinned version; nested dependencies are authored URIs and always go through the URI wrapper. A successful lookup with the same URI and CID may replace an unavailable pinned version; a different CID never satisfies it.

# External embed validation utilities

- `util/external/standard-site.ts` (`getStandardSiteRecordsForUri`, `validateStandardSiteRecordsForUrl`) and `util/external/index.ts` (`isExternalRecordUrlSafe`) are pure and synchronous over caller-supplied hydrated records, URLs, and a domain list: no I/O, config reads, mutation, or view construction.

# `app.bsky.embed.getEmbedExternalView`

- The handler normalizes the request to one record URI before hydration: an explicit `canonicalUri` always wins (ignoring `uris`, with no fallback); otherwise the legacy `uris` input selects the first `site.standard.document`, else the first `site.standard.publication`. Only the one URI is hydrated; dependencies come from existing hydration.
- Validate before building any view: Standard.site records via `getStandardSiteRecordsForUri` + `validateStandardSiteRecordsForUrl`, other records via `isExternalRecordUrlSafe(url, cfg.externalRecordsSafeDomains)`. Renderability is never the trust test.
- Validated records return `data` and `associatedRefs`/`associatedRecords`; failed validation returns only `unverifiedAssociatedRefs`/`unverifiedAssociatedRecords` and builds no view. The legacy `view` is returned for Standard.site records only. Both outputs and the legacy `view.external.associatedRefs` use the same index-aligned persisted subset, canonical first.
- Render-time hydration and persistence are separate. Hydration may include engagement records (recommendations, subscriptions, favorites) that back `likers`/`subscribers` previews; that is intentional. `collectAssociations` persists the canonical record when available (whatever its collection) plus only the extra collections opted in by `PERSISTED_DEPENDENCY_COLLECTIONS` (document → publication; gallery → gallery item and photo), to keep post records slim. It is not an engagement blacklist. A new persisted dependency collection needs an explicit entry; do not change hydration or views for this.
