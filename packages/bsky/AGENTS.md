# AppView hydration

- Endpoint-specific viewer block checks must honor `HydrateCtx.skipViewerBlocks` for the trusted moderation service, while preserving viewer block metadata and mute filtering.
- In `hydration/external.ts`, keep shared types above `ExternalHydrator`; place helpers and their specific types below the class.
- `ExternalHydrator` generic record lookups decode record bodies without collection-specific validation. Validate against the relevant Lexicon before using typed fields; do not apply parse-mode defaults to stored records.
- `Views.externalRecordView` consumes `HydrationState.externalRecords` (latest versions), `externalRecordBacklinks` (target URI → available source URI samples), and `externalRecordBacklinkCounts`. Hydrate referenced publications, gallery item/photo records, backlink source records, labels, and profiles before building views. Counts are independent of the sampled previews.
- Modality builders do not resolve web URLs. Grain galleries use their record AT URI; Streamplace uses a declared HTTP(S) URL or falls back to its AT URI. A stream is active only without `endedAt` and with a `lastSeenAt` within `LIVESTREAM_HEARTBEAT_WINDOW_MS` (2 minutes) of `now`, on either side; record `idleTimeoutSeconds` and `createdAt` are ignored.
- Atmosphere Explore uses each worker item’s `canonicalUri` as its sole hydration/view root; a missing or invalid root skips the item with no fallback or backfill. With the `AtmosphereExploreArticlesIrisEnable` gate off, worker groups also supply articles; with it on, up to 10 Iris `site.standard.document` roots (fetched concurrently with the worker, no fallback) are the exclusive article source: worker articles are ignored and worker location/topic selection does not apply to them. Every list is capped at 10: selected record-backed lists (including Iris articles) are shuffled before hydration with scheduled featured items first, and presentation preserves that order; apps are capped at 10 in worker order. Upstream ingestion is best-effort per item: after a successful decode, malformed banners, groups, app cards, and Iris articles (and invalid Iris rec IDs) are skipped whole without failing siblings or the request, only the first 100 worker / first 10 Iris entries are examined, and a gated-on Iris result is never replaced by worker articles. Transport, redirect, JSON, timeout, and decoded-byte failures still map to 502/504. The bounded Iris client wrapper is cached per source `Client`; headers and abort signals stay request-scoped. Each list is an `{ items, recIdStr? }` section; only Iris articles set `articles.recIdStr`. Keep root validation in `getAtmosphereExploreTab.ts`; one shared hydration traversal discovers publications and other dependencies.
- Exact-ref hydration maps are keyed by the branded `ExactRecordKey` from `genericRecordKey({ uri, cid })`, not URI alone; `parseGenericRecordKey` accepts only those keys and throws on malformed ones. Unavailable records are `null`, and takedowns are excluded unless explicitly requested.
- Preserve `truncated` from actor backlink lookups: an empty target entry in a truncated batch does not prove the actor has no links.
- Generic external-view wrappers populate only the generic indexes (no `siteStandardDocuments`/`siteStandardPublications`) and follow a document's publication through normal dependency discovery (a second lookup after the document, with its own labels and profiles). Saved-post hydration still uses pinned strongRefs and the specialized maps; never replace a pinned publication with its latest version.
- `ExternalHydrator.getSiteStandardRecordsByRef` is specialized hydration for saved-post pinned strongRefs, built on the generic exact lookups; it never resolves publications.
- Pass all external URIs to `Hydrator.hydrateExternalViewDependencies`; dispatch by URI collection and validate records inside it. Batch new dependencies through `hydrateEmbedExternalViewFromUris`, sharing a `seenRecordKeys` set (including null lookups) across nested passes. Follow only complete DID-based record URIs.
- `hydrateEmbedExternalViewFromUris` nulls each generic record (in `externalRecords` and `externalRecordsByRef`, keeping keys) that has an actionable takedown label (unless `includeTakedowns`) or an explicitly `null` owner actor, before dependency expansion. Hiding is per record: never propagate it to targets or dependencies, and leave backlink counts and samples unadjusted.
- Dependency dispatch in `hydrateExternalViewDependencies` may register several backlink queries per target (each with its own collection and limit; results are unioned) and discovers direct references (e.g. `document.site`, `gallery.item.item`) through `discoveredUris`; direct-only passes issue no backlink or count calls. Validate authored references with `recordUriOf`; do not validate dataplane backlink URIs.
- External hydration traversals share a `seenRecordKeys` set that both wrappers filter against at entry by `genericRecordKey(ref)` (bare URI for latest, `uri@cid` for exact), so each lookup runs once per traversal (null results stay seen). `ExternalHydrator.MAX_EXTERNAL_HYDRATION_PASSES` hard-caps chained batches (root is pass 1; `hydrationPass` is threaded through both methods and never reset). At the cap, keep partial state, leave skipped URIs unseen, and warn.
- External-view counts, backlink pages, and nested dependency batches are best-effort: log failures and leave their state absent (a successful empty page is `[]`), and builders consume partial state, so galleries may be empty. Root fetch errors still propagate. Don't add failure-policy machinery.
- Thread the optional `hydrationMetrics` tracker through every nested external hydration call (wrappers and `hydrateExternalViewDependencies`). Only the call without one owns the traversal and reports `events.externalHydrationTraversal` once; omitting it in a nested call double-reports. Count lookups at batch scheduling, never from map or seen-set sizes, and keep totals out of metric attributes.
- `hydrateEmbedExternalViewFromUris` and `hydrateEmbedExternalViewFromRefs` are thin wrappers over one pipeline and one collection dispatch. Latest lookups are identified by URI (`externalRecords`); exact versions by `genericRecordKey({ uri, cid })` (`externalRecordsByRef`). Both identities share `seenRecordKeys`, and one never implies the other; a latest fetch does not mark its returned version as an exact lookup. Dependency discovery takes `ItemRef[]` and inspects every pinned version; nested dependencies are authored URIs and always go through the URI wrapper. A successful lookup with the same URI and CID may replace an unavailable pinned version; a different CID never satisfies it.

# External embed validation utilities

- `util/external/standard-site.ts` (`getStandardSiteRecordsForUri`, `validateStandardSiteRecordsForUrl`) and `util/external/index.ts` (`isExternalRecordUrlSafe`) are pure and synchronous over caller-supplied hydrated records, URLs, and a domain list: no I/O, config reads, mutation, or view construction.

# `app.bsky.embed.getEmbedExternalView`

- The handler normalizes the request to one record URI before hydration: an explicit `canonicalUri` always wins (ignoring `uris`, with no fallback); otherwise the legacy `uris` input selects the first `site.standard.document`, else the first `site.standard.publication`. Only the one URI is hydrated; dependencies come from existing hydration.
- Validate before building any view: Standard.site records via `getStandardSiteRecordsForUri` + `validateStandardSiteRecordsForUrl`, other records via `isExternalRecordUrlSafe(url, cfg.externalRecordsSafeDomains)`. Renderability is never the trust test.
- Validated records return `data` and `associatedRefs`/`associatedRecords`; failed validation returns only `unverifiedAssociatedRefs`/`unverifiedAssociatedRecords` and builds no view. The legacy `view` is returned for Standard.site records only. Both outputs and the legacy `view.external.associatedRefs` use the same index-aligned persisted subset, canonical first.
- Render-time hydration and persistence are separate. Hydration may include engagement records (recommendations, subscriptions, favorites) that back `likers`/`subscribers` previews; that is intentional. `collectAssociations` persists the canonical record when available (whatever its collection) plus only the extra collections opted in by `PERSISTED_DEPENDENCY_COLLECTIONS` (document → publication; gallery → gallery item and photo), to keep post records slim. It is not an engagement blacklist. A new persisted dependency collection needs an explicit entry; do not change hydration or views for this.
